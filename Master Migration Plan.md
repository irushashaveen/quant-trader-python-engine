# **Master Migration Plan: Institutional AI Quant Engine**

## **1\. Executive Summary & Current State Analysis**

Currently, your Python FastAPI engine operates on a basic REST API loop (\_monitor\_loop), polling Binance every 5 seconds for price updates using fetch\_ticker.

**Current Limitations:**

* **Latency & Rate Limits:** Polling every 5 seconds means you are blind to micro-second market dumps, which can result in blown stop-losses before the engine even registers the price drop. It also risks hitting Binance API rate limits.  
* **Database Blocking:** Writing real-time data synchronously to Supabase freezes the Python event loop, causing execution delays.  
* **State Vulnerability:** If the server restarts mid-trade, the local loop loses track of dynamic stop-loss orders.

This document outlines the blueprint to upgrade your system to an **Event-Driven, High-Frequency Architecture** leveraging asynchronous WebSockets, in-memory data structures, and decoupled databases.

## **Phase 1: Zero-Latency Data Ingestion (WebSockets)**

We are replacing the slow REST API polling loop with the ccxt.pro WebSocket library. This allows the engine to receive data pushed directly from Binance in milliseconds.

* **watch\_trades(symbol) (The Tape):** Streams every single live market buy and sell globally. This allows the engine to read the "Tape" and execute entries at the exact millisecond volume enters the market.  
* **watch\_order\_book(symbol) (L2 Deltas):** Streams live additions and cancellations of massive Limit Orders. This is crucial for detecting "Spoofing" (when whales place fake orders to manipulate retail traders).  
* **watch\_liquidations(symbol):** This is the ultimate institutional tool. It streams live alerts whenever retail traders' accounts are liquidated. We will use this to mathematically confirm Smart Money Concept (SMC) "Liquidity Sweeps."

## **Phase 2: Memory & Storage Management (Handling the Firehose)**

Streaming millisecond data directly into PostgreSQL or MongoDB will crash your 2GB server due to disk I/O bottlenecks. We are implementing a 3-Tier Storage Architecture:

### **A. Hot Storage (In-Memory / RAM) \- *For Split-Second Decisions***

* **Python collections.deque:** We will utilize Python's double-ended queue (deque) with a strict maxlen=10000 to store the incoming live ticks and order book deltas.  
* **Purpose:** As new trades arrive, the oldest ones automatically drop off, preventing RAM overflow. The engine will calculate the **Cumulative Volume Delta (CVD)** instantly from this in-memory list to decide if market pressure supports a trade entry.

### **B. Warm Storage (Redis) \- *For State Recovery***

* **Active Trade State:** The moment a trade is executed, its Order ID, Entry Price, and dynamic Trailing Stop Loss levels are serialized into Redis.  
* **Purpose:** If the Python server crashes or is taken offline for an update, the engine will query Redis upon reboot, locate the active trades, and seamlessly resume managing them.

### **C. Cold Storage (PostgreSQL & MongoDB) \- *For Analytics & Dashboards***

* **PostgreSQL (Relational Data):** Used strictly for completed trade journaling (PnL, Fees, Entry/Exit times) and aggregated 15-minute market snapshots (e.g., total 15m volume, funding rates). Your Next.js dashboard will query this for charts and Win Rate calculations.  
* **MongoDB (Unstructured Data):** Used to store the massive JSON audit logs generated by n8n and Gemini AI. Every trade will have a "Snapshot Document" explaining exactly *why* the AI decided to take the trade.

## **Phase 3: The Modular Architecture**

To prevent "spaghetti code," the monolithic main.py will be decoupled into four highly specialized plugins (modules):

1. **Data Ingestion Engine (data\_loader.py):** Handles the ccxt.pro WebSocket connections and manages the deque memory arrays. It aligns multi-timeframe candles (e.g., 4H and 15m) perfectly to prevent Lookahead Bias.  
2. **Technical & SMC Engine (smc\_engine.py):** The mathematics module. It detects Fair Value Gaps (FVG), Order Blocks, and Market Structure Shifts (CHoCH/BOS) based purely on the structured data provided by the loader.  
3. **Order Flow & Sentiment Engine (order\_flow\_engine.py):** The proprietary alpha module. It evaluates Open Interest and the Long/Short Ratio. If SMC says "Long" but Retail Traders are 85% Long, this engine will veto the trade to avoid whale liquidation hunts.  
4. **The Master Orchestrator (main.py):** The decision gate. It aggregates signals from the SMC Engine, the Order Flow Engine, and the Macro AI Agent (via n8n). It executes trades via Binance API only when all three confirm confluence.

## **Phase 4: Immediate Bug Fixes**

As we implement this architecture, we will simultaneously resolve two critical bugs noted in the current-state report:

1. **Asynchronous Database Writes:** All Supabase/PostgreSQL inserts will be wrapped in asyncio.to\_thread() or utilize asynchronous HTTP clients to ensure the main trading loop is never blocked.  
2. **Hedge Mode Verification:** The engine will query Binance account settings at startup (privateGetPositionSideDual) to verify if the account is in One-Way or Hedge mode, dynamically adjusting its order parameters to prevent execution failures.
